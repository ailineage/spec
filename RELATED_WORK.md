# Related Work

This document is informative. It positions AILineage relative to existing work. AILineage aims to complement, not replace, the systems below ([ADR-0003](adr/0003-embed-into-c2pa-and-in-toto.md)).

| Work | What it does | Relationship to AILineage |
| --- | --- | --- |
| [C2PA](https://c2pa.org/) / Content Credentials | Signed provenance manifests embedded in media (JUMBF), with actions, ingredients and `digitalSourceType`. | Primary carrier for media. AILineage rides inside as assertion `org.ailineage.lineage` and adds prompt commitment, escrow, principal and cross-modal lineage, which C2PA does not define. |
| [in-toto](https://in-toto.io/) attestations / [SLSA](https://slsa.dev/) | Signed statements about software artifacts (subject digest + typed predicate) in DSSE envelopes; SLSA defines build provenance levels. | AILineage is an in-toto predicate (`https://ailineage.org/predicate/v0.1`) for AI-generated code and artifacts. SLSA covers the build; AILineage covers the generation step before it. |
| [Sigstore](https://www.sigstore.dev/) | Keyless signing with short-lived certificates (Fulcio) and a transparency log (Rekor). | Planned future signature profile ([ADR-0005](adr/0005-signature-suites.md)); also a model for a Registry transparency log (THREAT_MODEL T12). |
| [CycloneDX](https://cyclonedx.org/) ML-BOM / AI-BOM | Bill of materials for ML models, datasets and their pedigree. | Describes models and datasets; AILineage describes individual outputs. Mapping in SPEC.md §11.3. |
| [OpenLineage](https://openlineage.io/) | Open standard for data pipeline lineage events (jobs, runs, datasets). | Similar DAG thinking, but for datasets and jobs, unsigned, operational. AILineage is per-artifact, signed and evidentiary. An OpenLineage facet could reference AILineage `artifact.id`. |
| [W3C PROV](https://www.w3.org/TR/prov-overview/) | Conceptual model of provenance: entities, activities, agents. | AILineage is a concrete, signed profile: artifact ≈ entity, generation ≈ activity, actor ≈ agent, `parents` ≈ `wasDerivedFrom`/`used`. |
| [IPTC Digital Source Type](https://cv.iptc.org/newscodes/digitalsourcetype/) | Controlled vocabulary for how media was created (`trainedAlgorithmicMedia`, …). | Used for the C2PA mapping of `generation.kind`. |
| [OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) | Attributes for tracing LLM calls (`gen_ai.request.model`, token usage, …). | Operational telemetry, not evidence. A planned exporter turns `gen_ai.*` spans into manifests (roadmap phase 5). |
| [DZone: "Git Blame Isn't Enough: Building Verifiable Provenance for AI-Generated Code"](https://dzone.com/articles/verifiable-provenance-ai-code) (Mopathi, 2026) | Argues that AI code generation is a supply-chain event needing provenance that links intent, context, model, edits and commits. | Same problem statement for code. AILineage's sidecar, header comment and Git-notes embedding plus `context_refs` and `previous_version` chains are a concrete format for it. |
| [Cisco Model Provenance Kit](https://github.com/cisco-ai-defense/model-provenance-kit) | Open-source CLI that fingerprints models to detect derivation from known base models. | Verifies *model* lineage from weights; AILineage records *output* lineage and the claimed model. MPK-style fingerprints could back `model.version_hash` claims (THREAT_MODEL T3). |
| Watermarking (e.g. SynthID) | Imperceptible signals embedded in content by the generator. | Orthogonal and complementary: survives some stripping but carries little information. AILineage does not generate watermarks; Verifiers may read them as information. |
| AI content detectors | Classify content as likely AI or human. | Explicitly not what AILineage does (SPEC.md §1.2); detection results are probabilistic and not attributable. |
