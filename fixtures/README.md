# Fixtures

Conformance fixtures for `ailineage/0.1`. SDKs SHOULD run all of them as golden tests.

- `valid/` — manifests that MUST pass schema validation and whose hashes, signatures and timestamps MUST verify.
- `invalid/` — manifests that MUST be rejected. Each one changes exactly one thing in a valid fixture and records the violated REQ-ID in `"_note"`.
- `data/` — the sample artifacts the valid fixtures describe. Every `artifact.id`, `parents[].id`, `context_refs[]` and digest is computed from these bytes. `data/salts.json` and `data/openings.json` hold the **TEST ONLY** salts and openings (plaintext + salt) of every salted prompt commitment; in production they would exist only in escrow or with the principal.
- `keys/` — **TEST ONLY** signing keys and the freetsa.org TSA certificates ([keys/README.md](keys/README.md)).
- `vectors/` — canonicalization test vectors (also rendered in CANONICALIZATION.md).
- `index.json` — machine-readable test plan for SDK golden tests: each case names a manifest, the artifact file (or `null` for structure-only cases), how the manifest is located (`out-of-band`, `embedded`, `sidecar`) and the expected state and reason, plus the TEST ONLY trust policy (signing keys, TSA root). Generated and checked by `regen.py`.
- `regen.py` — generator and checker, the only code in this repository.

## How the fixtures are made

`make fixtures-regen` runs `fixtures/regen.py regen`, which:

1. writes the sample data: a 64×64 PNG gradient, an inpainted variant, a 0.1 s 440 Hz WAV, text and Go files, a ComfyUI API-format workflow;
2. builds every manifest from those bytes;
3. signs it with the test key (`EdDSA`, or `ES256` for fixture 04) over JCS of the manifest without `signature`;
4. requests an RFC 3161 token from freetsa.org over SHA-256 of the signature bytes;
5. derives the invalid fixtures, the examples and the generated blocks in README.md and CANONICALIZATION.md.

Signatures and tokens are reused when the signed content has not changed, so regeneration is idempotent. `data/clip.mp4`, `data/image-64.jpg` and `data/image-64.webp` are not generated by the script. They were produced once from `image-64.png` with FFmpeg 8.1 and libwebp 1.6.0 and are committed as is:

```sh
ffmpeg -loop 1 -i image-64.png -t 1 -r 4 \
  -vf "zoompan=z='1+0.03*on':d=4:s=64x64:fps=4,format=yuv420p" \
  -c:v libx264 -preset veryslow -crf 30 -fflags +bitexact -flags:v +bitexact \
  -map_metadata -1 -movflags +faststart clip.mp4
ffmpeg -i image-64.png -frames:v 1 -c:v mjpeg -q:v 3 -pix_fmt yuvj420p \
  -fflags +bitexact -flags:v +bitexact -map_metadata -1 image-64.jpg
cwebp -lossless -exact -metadata none image-64.png -o image-64.webp
```

`make validate` runs `regen.py check`, which recomputes every identifier from `data/`, verifies each opening against its salted `prompt.hash` or `system_prompt_hash`, verifies each signature with the test keys, and verifies each timestamp against the freetsa.org root.

**Stand-in values.** Weights are not shipped with the spec. `model.version_hash` values of self-hosted models (`flux-schnell`, `flux-fill-dev`, `acestep-v15-turbo`, `wan2.2-ti2v-5b`, `llama-3.3-70b-instruct`) are SHA-256 over the string `TEST-ONLY weights stand-in: <name>`, not over real weights. `build:` values for hosted models are illustrative. Escrow ids and DIDs other than the signing key are illustrative too.

Invalid fixtures keep the signature of the fixture they were derived from, which no longer matches the mutated content. They test structure only.
